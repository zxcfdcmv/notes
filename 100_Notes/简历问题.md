# CI/CD 动态 Agent 降低 40% 计算成本
在 **Jenkins 控制台 -> 节点管理 -> Pod Template** 中，或者通过声明式脚本（Jenkinsfile）来配置 `Kubernetes plugin`：

- **Pod 生命周期管理**：将 `retentionStrategy`（保留策略）设置为 `PodCleanUp.success()` 或配置 `idleMinutes: 1`。这意味着当流水线结束（成功/失败），K8s 会立即回收该 Pod 占用的核心资源（CPU/Memory），从而将非工作时间的“静态资源闲置率”降为 0。
- **解决冷启动（ImagePullBackOff）延迟**：动态创建 Pod 最怕每次都重新拉取几百兆的 Docker 镜像。
    
    - **做法**：在 K8s 节点上配置 **ImagePullPolicy: IfNotPresent**。
    - **进阶**：使用 DaemonSet 在所有 Node 节点上提前预热（缓存）好常用的基础构建镜像（如包含 `Maven/Node/Go` 环境的自定义镜像）。

# 监控重构，告警从 5 分钟降至 30 秒，误报率降 60%
秒级响应的底层配置 (Prometheus & Alertmanager)

- **调整抓取频率（控制在合理范围）**：不能盲目把全量指标都改成 10s 抓取。针对核心系统指标（如 K8s 节点的 CPU、内存、网络 IO、业务组件的 Http Request），在 `prometheus.yml` 中设置独立的 `scrape_interval: 10s` 和 `evaluation_interval: 10s`。
- **Alertmanager 告警等待管道优化**：
  ```yaml
  # alertmanager.yaml 核心片段
route:
  group_wait: 5s       # 收到第一条告警后，只等待5秒看有没有同组告警，然后立即发送
  group_interval: 1m   # 同一组告警如果触发了新的，1分钟内合并发送
  repeat_interval: 3h  # 已经发送过的告警，3小时内不再重复轰炸
  ```

降低误报率 60% 的表达式重构（防抖与降噪）

- **旧的粗暴写法（易误报）**：`100 - (avg by(instance) (rate(node_cpu_seconds_total{mode="idle"}[1m])) * 100) > 90` —— 只要 CPU 一瞬间冲高超过 90% 就会立刻报警。
- **重构后的精细化写法（降噪）**：
  ```promql
  # 使用 5分钟的滑动窗口求平均，且必须在 prometheus 中持续（for）满足 1 分钟才触发
expr: avg_over_time(instance:node_cpu_utilization:ratio[5m]) > 0.90
for: 1m
  ```
- **抑制规则（Inhibition Rules）**：配置“当宿主机挂掉（`NodeDown`）时，自动抑制（挂起）该宿主机上所有 Pod 挂掉（`PodMissing`）的告警”，防止单点故障引发成百上千条衍生告警轰炸（告警风暴）。

# 慢查询优化使数据库负载下降 40%
深度排查与慢 SQL 定位

- **开启慢日志**：设置 `long_query_time = 0.5`（超过 0.5 秒即为慢查询），通过 `pt-query-digest /var/log/mysql/mysql-slow.log` 导出分析报告。
- 发现 Top 1 的高频慢查询是一个用户订单查询接口：
  ```
  SELECT * FROM orders WHERE user_id = 10023 ORDER BY create_time DESC LIMIT 20;
  ```

具体实施三步走

- **步骤一：执行计划分析（EXPLAIN）**：使用 `EXPLAIN` 发现该 SQL 的 `type` 字段为 `ALL`（全表扫描），或者 `rows` 扫描了上百万行，且 `Extra` 提示 `Using filesort`（使用了磁盘文件排序，极其消耗 CPU）。
- **步骤二：建立联合索引（关键动作）**：
  ```
  -- 创建 user_id 和 create_time 的联合索引
ALTER TABLE orders ADD INDEX idx_userid_createtime (user_id, create_time DESC);
  ```
  ==利用索引的有序性，直接消除了 `Using filesort`，将查询效率从秒级提升到毫秒级（`type` 变为 `ref`）。==
- **步骤三：改造为覆盖索引（避免回表）**：将业务层面的 `SELECT *` 严格修改为具体需要的字段（如 `SELECT id, order_no, price FROM...`），让查询直接在索引树上完成返回，不需要再去回表扫描聚簇索引，大幅降低了磁盘 I/O。
- **步骤四：数据过期策略与 Redis 兜底**：配合业务层，将超过一年的历史订单冷数据归档到冷存储中；同时针对高频访问的前几页订单数据，在应用层引入 Redis 缓存，设置 5 分钟过期时间，降低直接击穿到数据库的概率。
- **结果**：数据库主机的 CPU 利用率从经常性的 85% 飙红，稳定回落到 45% 左右，整体负载下降约 40%。
