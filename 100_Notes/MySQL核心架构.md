# Server层
> [!note] 除了**数据存储与提取**之外的所有事情都在这里完成

## 连接器Connector
- **核心职责**：负责与客户端**建立连接、获取权限、维持和管理连接**。
- **工作机制**：
    - 校验客户端输入的用户名和密码。如果失败，返回错误提示。
    - 认证通过后，连接器会去权限表里**查出当前用户拥有的权限**。此后这个连接里的权限判断，都将依赖此时读到的权限数据（这意味着用户建立连接后，管理员修改了该用户的权限，对已存在的连接不会生效，只有新建连接才会生效）。
    - 负责管理空闲连接，超时未操作会自动断开（由 `wait_timeout` 参数控制，默认 8 小时）。

## 查询缓存Query Cache
> [!note] 当执行查询时，会先看缓存里有没有相同的 SQL 语句和结果，如果有就直接返回，MySQL8.0版本后==已删除==

- **被删除的原因**：**缓存的失效非常频繁**。只要一个表有任何一条数据被更新，这个表对应的**所有查询缓存都会被清空**。对于写多读少的业务，查询缓存的命中率极低，还会带来额外的维护开销，得不偿失。

## 解析器Parser
- **核心职责**：把客户端传过来的普通文本 SQL 语句，解析成 MySQL 能认识的内部数据结构。
- **工作机制**：
    - **词法分析**：将 SQL 拆分成一个个独立的单词。识别出关键字（如 `SELECT`）、表名、列名等。
    - **语法分析**：根据语法规则，判断这个 SQL 语句是否满足 MySQL 的语法。如果不满足，就会抛出经典的异常：`You have an error in your SQL syntax`。

## 预处理器Preprocessor
- **核心职责**：进一步检查解析树的合法性。
- **工作机制**：
    - 检查 SQL 语句中的表名、列名是否存在。
    - 检查用户是否有操作该表或该列的权限。

## 优化器Optimizer
- **核心职责**：**决定 SQL 语句的执行方案**。这是最影响性能的环节。
- **工作机制**：
    - 当一条 SQL 有多种执行路径时（例如表里有多个索引，或者多表关联查询），优化器会基于 **成本（Cost）** 评估，选择它认为效率最高的一种。
    - **常见优化动作**：决定使用哪个索引；决定多表连接（Join）时的各个表的加载顺序。

## 执行器Executor
- **核心职责**：开始执行 SQL 语句，负责与存储引擎交互。
- **工作机制**：
    - 在执行前，先验证当前用户对该表有没有执行该语句的权限（如没有，直接报错）。
    - 如果有权限，就根据优化器生成的执行计划，一步步**调用存储引擎提供的 API 接口**获取数据。
    - 将存储引擎返回的数据收集起来，最终返回给客户端。

# 存储引擎层
> [!note] 只负责数据的存储和提取

- **插件式架构**：MySQL 支持多种存储引擎，它们都实现了相同的 API 接口。Server 层不关心底层数据怎么存，只通过接口收发数据。
- **核心引擎**：

    - **InnoDB**：MySQL 5.5.5 版本开始的**默认存储引擎**。全面支持事务（ACID）、行级锁、外键以及崩溃恢复能力，是绝大多数业务的首选。
    - **MyISAM**：早期的默认引擎。不支持事务，只支持表级锁，但读取速度快，占用资源少，目前极少在核心业务中使用。
    - **Memory**：数据全部存放在内存中，读写速度极快，但断电后数据会全部丢失，常用于临时表。

|对比维度|InnoDB|MyISAM|
|---|---|---|
|**事务支持**|**支持**（具备 ACID 特性）|不支持|
|**锁粒度**|**支持行级锁**、表级锁|仅支持表级锁|
|**外键**|**支持**|不支持|
|**崩溃恢复**|**支持**（依赖 redo log）|不支持|
|**主键**|必须有主键，默认自增|可以没有主键|
|**核心应用场景**|绝大多数业务、高并发、需要事务的场景|读多写少、不需要事务、对原子性无要求的场景|
